01 THE SETUP

What FleetGate is

FleetGate is the command gateway for the Meridian delivery-drone fleet. Every command requires a Bearer token signed by the fleet-ops key using ES256. Anyone can request a short-lived viewer token. Releasing the vault — where the flag lives — requires a fleet-admin token, which the fleet-ops team only mints offline.

The service exposes four endpoints:

GET / Service info & algorithm details
GET /.well-known/jwks.json EC P-256 public key
POST /api/token/guest Issues a short-lived viewer token
POST /api/command Executes fleet commands

02 RECONNAISSANCE

What the endpoints actually told us

1
GET / — token structure confirmed

Service uses ES256 compact JWS. Required claims: iss = "fleet-ops", a future exp, and role in {viewer, operator, fleet-admin}. Signatures are raw R‖S, 64 bytes, base64url-encoded.

2
GET /.well-known/jwks.json — public key retrieved

One EC P-256 key, kid fleet-ops-2026-11. The x and y coordinates each decode to 32 bytes. This is the only key the verifier trusts.

3
POST /api/token/guest — role escalation blocked

Issues viewer tokens regardless of what role you request. Sending release-flag with a viewer token returned 403 requires role fleet-admin. We need to forge a fleet-admin token.

03 DEAD ENDS

Everything that didn't work

The obvious JWT attacks were all tried first. Each one was blocked cleanly.

✗
alg = none

Tokens with "none", "None", or "NONE" were rejected as malformed. The parser checks for this.

✗
HS256 key confusion

HS256 signed with the public key (PEM and DER forms) returned "only alg ES256 is accepted". The algorithm is pinned — no confusion possible.

✗
kid injection

Path-traversal and SQL-style kids returned "unknown kid". The kid is a lookup key, not a filesystem path or query parameter.

✗
Embedded JWK in header

A token with its own jwk in the header was rejected with "signature verification failed". The server ignores embedded keys entirely.

✗
Wrong signature length / encoding

63-byte signatures and DER-encoded signatures were rejected for incorrect length. A random valid-length 64-byte raw signature reached the check and returned "signature verification failed" — confirming the format is R‖S, 64 bytes flat.

04 THE VULNERABILITY

Probing the boundary of r and s

ECDSA requires both r and s to be integers in the range [1, n−1]. If the verifier doesn't check this before computing, it can be exploited. We tested four cases:

r = 0, s = 1 REJECTED 401
r = n, s = 1 REJECTED 401
r = 1, s = n REJECTED 401
r = 0, s = 0 (64 zero bytes) ACCEPTED 200

All-zero signature. 64 bytes of nothing. The server said yes.

06 WHY IT WORKED

The math behind the bypass

ECDSA VERIFICATION — STEP THAT WAS SKIPPED

Standard ECDSA verification must first assert: 1 ≤ r ≤ n−1 and 1 ≤ s ≤ n−1. If either value is out of range, the signature must be rejected before any arithmetic begins.

This service skipped that check. With s = 0, the verifier tries to compute w = s⁻¹ mod n. Zero has no modular inverse — the verifier should abort. It didn't.

With s = 0 and r = 0, the resulting elliptic-curve point collapses to the point at infinity. Its x-coordinate comparison against r then passes — because r is also zero. The forged signature is accepted.

CVE-2022-21449

This is the same behaviour as the well-known Java JDK "Psychic Signatures" bug, where the standard ECDSA verifier in Java accepted all-zero signatures for any message and any public key. The fix is always the same: validate r and s are in [1, n−1] and treat the point at infinity as an invalid result, before touching any arithmetic.
